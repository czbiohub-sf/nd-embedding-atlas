NDEA supports two custom-node forms. They share exact node definitions at
runtime but carry different trust and portability guarantees.

## Executable plugins and declarative node assets

| Form                   | Contents                                       | Executes code | Typical use                                      |
| ---------------------- | ---------------------------------------------- | ------------- | ------------------------------------------------ |
| Custom-node plugin     | Manifest, bundled ESM client, static assets    | Yes           | New transforms, mounted views, host integrations |
| Declarative node asset | Versioned graph, promoted ports and parameters | No            | Reusable pipelines authored in the Canvas        |

A plugin is trusted code. Its client runs in the application origin with normal
browser privileges. Manifest validation limits compatibility, registration,
and served files; it does not sandbox JavaScript. Permission entries disclose
high-risk behaviour to users and tooling.

A node asset is inert JSON. It can compose built-in nodes, plugin nodes, and
other node assets, but it cannot add executable behaviour. Dependencies must be
acyclic.

## Canonical terms

- **Plugin package** — installable executable contribution with one strict
  manifest and one self-contained client entry.
- **Node definition** — immutable author contract for one exact node type
  reference: identity, ports, config, capabilities, evaluation, lazy module,
  documentation, and portable presentation hints.
- **Node module** — lazily loaded implementation for per-instance runtime or
  Body mounting.
- **Node host** — capability-gated services for one live node occurrence.
- **Node runtime** — per-instance compute and lifecycle state.
- **Body** — mounted visual content whose DOM identity survives Canvas, Stage,
  and fullscreen moves.
- **Node asset** — declarative, versioned subgraph published as a reusable node.
- **Node instance** — one graph record referring to one exact definition.

Workspace owns document, layout, persistence, and composition. These concerns
never enter `@ndea/sdk` author contracts.

## Independent version axes

Never substitute one version for another.

| Axis                       | Shape                | Governs                                                      |
| -------------------------- | -------------------- | ------------------------------------------------------------ |
| Manifest schema version    | Integer, currently 1 | Serialized `ndea-plugin.json` shape                          |
| Plugin package version     | Semantic version     | Distribution release of the whole plugin                     |
| SDK version range          | Semantic range       | Public `@ndea/sdk` contract accepted by the plugin           |
| Host version range         | Semantic range       | NDEA application releases accepted by the plugin             |
| Node type version          | Semantic version     | Exact executable or declarative node interface and behaviour |
| Node config version        | Integer              | Migration chain for one node definition's config             |
| Node asset version         | Semantic version     | Published declarative graph definition                       |
| Workspace document version | Integer              | Persisted Workspace schema and migration boundary            |

The catalogue keys definitions by exact `nodeTypeId@nodeTypeVersion`. A newer
semantic version may become the palette's current choice, while restored
instances continue to request their exact version.

## Plugin discovery and startup

The server resolves project plugins first, then enabled user plugins. For each
package it:

1. resolves the real package root and containment boundary;
2. reads and validates `ndea-plugin.json`;
3. checks SDK, host, and platform compatibility;
4. reads only the declared client and static assets;
5. rejects runtime imports in the client entry;
6. snapshots approved bytes under content-addressed URLs.

The browser imports each validated client, collects its registration batch,
validates ownership and definition invariants, then commits the batch. One
failure cannot partially register a plugin. The catalogue freezes before the
Workspace document restores.

Project paths come from top-level YAML `plugin_paths` entries and remain inside
the YAML directory. User packages live under
`~/.ndea/plugins/packages/`; ordered enablement state lives in
`~/.ndea/plugins/config.json`.

## Linked and embedded node assets

Publishing a selected subgraph creates an exact semantic node asset version.
Promoted ports form its public graph interface. Promoted parameters point to
specific inner node config paths and carry validated defaults.

A Workspace instance can preserve either source strategy:

- **Linked** — records the source and exact node asset reference. If available,
  NDEA uses only matching source bytes. An optional exact fallback preserves
  offline execution.
- **Embedded** — stores the exact definition in the Workspace. It remains
  portable without the original library.

NDEA never silently replaces an exact linked record with bytes from another
source, even when the asset ID and version match. Missing definitions remain
unresolved and preserve their graph record, config snapshot, edges, position,
and provenance for later recovery.

Node assets may nest. Runtime expansion gives every inner node and wire a
deterministic outer-instance-scoped ID. Recursive dependencies, duplicate
promoted targets, duplicate inner wires, invalid ports, and empty output
interfaces are rejected before publication.

## Authoring lifecycle

Canvas authoring follows one transactional path:

1. Select a same-level connected subgraph.
2. Publish it as a new asset ID and semantic version, or edit an existing asset
   and publish a strictly newer version.
3. Choose linked provenance, embedded Workspace bytes, or linked provenance
   with an exact embedded fallback.
4. Replace the selected subgraph with one node instance only after publication
   and graph registration succeed.
5. Persist the Workspace document and user asset library atomically; rollback
   restores the previous document and library snapshot on failure.

Asset libraries are immutable snapshots. Runtime reconciliation rebuilds nested
expansions when any exact dependency changes, rebinds sinks, and restores
previous state when refresh fails.
