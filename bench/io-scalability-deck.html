the problem

The data outgrew the memory.

A browser + Bun app: WebGPU scatter, Mosaic cross-filter, native DuckDB. It reads single-cell AnnData/zarr. Targets were ~100k obs. The roadmap is 5–10 million.

the method

One lever per cycle. The data decides.

An autonomous-iteration loop (the Karpathy / autoresearch pattern): a single scalar metric, fast verification, git as memory. No guessing — measure, change, re-measure, keep or revert.

cycle 1a — file-backed duckdb

The obvious fix… wasn't.

Flip DuckDB from :memory: to a file + memory_limit so it pages out-of-core. Prediction: big RSS drop. Reality: it depends entirely on where the memory lives.

zarr path @ 1M
4,726 → 4,682 MB
peak unchanged — DuckDB resident 848→67 MB, but the 3.9 GB JS pipeline is untouched. REJECTED as a standalone fix.
parquet path @ 5M
3,402 → 615 MB
−5.5× — once data is columnar-on-disk, out-of-core works beautifully.

Lesson kept: file-backed DuckDB is the right substrate — but useless while JavaScript still holds the whole dataset. The seam stays; the search continues.

cycle 2 — diagnosis

Three copies of the data, all at once.

A forced GC didn't move RSS (it's sticky — the runtime keeps freed pages). So the metric that matters is the peak allocation high-water. We traced where it comes from:

  • Copy 1 — zarr-decoded source. Every obs column read into JS typed arrays.
  • Copy 2 — per-column conversions. Categoricals decoded back to full string arrays — undoing AnnData's compact codes.
  • Copy 3 — a full flechette Arrow Table built before the DuckDB Appender drains it.

The key realization: the Appender appends per-row values — it never needs the Arrow Table. It could read straight from the source.

commit 3080fa7 · RSS-sticky lesson → optimize PEAK, not post-hoc release

research interlude — 19 verified claims

Stand on the literature, not vibes.

A deep, adversarially-verified research pass grounded the next move in primary sources — and the concepts converged on one answer.

  • Bounded chunk-streaming is the fix — and it's language-independent (MonetDB/X100: process cache-resident vectors, not full columns).
  • Don't rewrite DuckDB — its out-of-core hash aggregation degrades gracefully (the only engine to finish TPC-H SF128 in 32 GB).
  • Keep categoricals dictionary-encoded end-to-end; cross-filter sits in the late-materialization regime (Abadi).
  • Rust verdict: defer. The win is the discipline, not the language. One experiment would decide it.

cycle 3 — what it settled

Two answers for the price of one cycle.

the rust question — answered
No, not for ingest.
The research's decisive experiment: after streaming-TS, does the JS side drop near DuckDB's footprint, or does zarr decode stay a multi-copy wall? → It dropped to ~233 MB. zarr decode is not the wall. A second native artifact (per-platform builds, FFI, broken single-binary) buys nothing here. The win was the discipline, exactly as predicted.
the guard earned its keep
A real bug, caught.
is_primary_data — a boolean obs column — was coming out "". flechette's utf8 builder silently empties non-strings: boolean columns were being dropped in production. Fixed in both paths; verify then passes 0. The correctness gate found a latent data-loss bug nobody was looking for.
cycle 4a — the full out-of-core stack

Now the two wins compose.

Streaming ingest (JS copies gone) + file-backed DuckDB (Cycle 1a's substrate pages the native table) = the complete out-of-core stack on real DuckDB.
